### 決めたこと・その理由
| 決めたこと | 理由 |
|---|---|
| Next.js 16 の Cache Components を無効化 | ほぼ全画面がログイン必須で cookie を読む。有効のままだと画面ごとに Suspense の境界が要り、1.5日の開発では手間に見合わない |
| DB ドライバは `@neondatabase/serverless` の Pool（WebSocket） | HTTP ドライバはトランザクションが使えない。R3 の判定と保存を1つのトランザクションでやりたい |
| Neon・Vercel の関数ともにシンガポール（`sin1`） | Vercel の既定はアメリカ東部。DB と離れていると問い合わせのたびに太平洋を往復する |
| 認証は Better Auth を自前の DB に持つ（Neon の Better Auth サービスは使わない） | ユーザー表を tasks などと同じ DB に置き、外部キーでつなぐため |
| PDF 用フォントは Noto Sans JP の TTF（Regular・Bold）を `public/fonts/` に同梱 | @react-pdf/renderer は woff2 を読めない。計画書のリスク表どおり、先に日本語1行で試して文字化けしないことを確認した |
| pnpm 12 で esbuild のインストール処理だけ許可 | 許可しないと shadcn の初期化が失敗する |
| 開発中は Neon の `dev` ブランチを使い、本番は `production` ブランチ | 本番 DB で直接試さないため |

### 起きた問題と対処
- **本番が全ページ 404**：Vercel プロジェクトを空のリポジトリから作ったため、フレームワーク設定が空のままだった。ビルドは成功していたが `public/` しか配信されていなかった。`vercel.json` に `"framework": "nextjs"` を書いて固定した。
- **CI 環境で型チェックが失敗する**：`LayoutProps` などの型は Next.js がビルド時に作る。`typecheck` を `next typegen && tsc --noEmit` にして、先に型を作るようにした。

### 残課題
- 新規登録は誰でもできる。招待した人だけ登録できる制限はタスク5で入れる
- `/api/pdf-test` はタスク11で本実装に置き換えるときに消す
- PR ごとのプレビュー URL では、`BETTER_AUTH_URL` と送信元が違うためログインが弾かれる可能性がある。必要になったら `trustedOrigins` に足す

  - R0：土日の予定日・実績日 → 拒否。祝日は DB では通る（設計どおり。サーバーで拒否する）
  - R1：成果物が空白だけ・完了なのに URL もメモもない → 拒否
  - R2：担当者なし・プロジェクトのメンバーでない担当者 → 拒否

- 型チェック・lint：成功

### 決めたこと・その理由
| 決めたこと | 理由 |
|---|---|
| 日付列は `date` 型、TypeScript では `"YYYY-MM-DD"` の文字列 | `Date` にするとタイムゾーンで1日ずれる事故が起きる |
| 土日禁止を DB の CHECK にも入れた（`extract(isodow …) < 6`） | 指示書では DB の守りは R3 だけだったが、土日は DB でも判定できるので入れた。祝日は年ごとに変わるので DB では判定せず、サーバーで止める |
| 完了（100%）には成果物 URL かメモが必要、を CHECK に入れた。メモ用に `tasks.completion_note` 列を追加 | R1 の「完了にするには URL かメモが必須」を DB でも守るため。指示書の列一覧にはメモの列がなかった |
| タスクのフェーズと担当者を、複合外部キーで「同じプロジェクトのもの」に限定 | 別プロジェクトのフェーズに付ける・メンバーでない人を担当にする、を DB で防ぐ |
| 担当者の外部キーは `no action`（`restrict` ではない） | `restrict` だと、プロジェクトを消したときの連鎖削除の途中で弾かれる。`no action` は文の最後に判定するので、連鎖削除は通り、担当タスクが残ったままメンバーだけ外すのは防げる |
| 週の最終曜日は 1〜5（ISO 曜日：月=1 … 金=5）に限定 | 週の最終「稼働日」なので、土日は選べない |
| 目的とフェーズの親子関係は CHECK で形だけ守る（目的は親なし、フェーズは親あり） | 「フェーズの親が目的であること」は CHECK では書けないので、サーバーで確認する |
| 招待に `invited_by`、プロジェクトに `updated_at` を追加 | 誰が招待したかを残すため、更新日時を一覧で使うため |

### 残課題
- 本番 DB（Neon の `production` ブランチ）にはまだ `0001`・`0002` を適用していない。タスク5の画面を本番に出す前に適用する
- 祝日の拒否、「フェーズの親が目的であること」の確認、`23P01` を日本語のエラーに変える処理は、サーバー側（タスク4以降）で作る

### 決めたこと・その理由
| 決めたこと | 理由 |
|---|---|
| 祝日は `@holiday-jp/holiday_jp` の `holidays`（"YYYY-MM-DD" がキー）を直接引く | `Date` を渡す API はタイムゾーンでずれうる。文字列のキーなら日付がずれない。データは 2050 年まである |
| `nextWorkday` / `previousWorkday` は「その日を含まない」次・前の稼働日。含む版は `workdayOnOrAfter` / `workdayOnOrBefore` | 指示書は `nextWorkday(date)` とだけ書いていた。どちらの意味でも使うので 2 つに分けた |
| バッファは「締切日以前の最後の N 稼働日」。最終タスクはその前日の稼働日までに終える | R0 で「バッファ日数は稼働日で数える」ため。例：締切 2027-01-08・バッファ 5 → 予備期間 01-04〜01-08、最終タスクは 2026-12-31 まで（01-01 は元日）。締切が休日なら直前の稼働日から数える |
| バッファ残 =「最終タスクの翌日〜締切日」の稼働日数 | ダッシュボード・PDF の「バッファ残」に使う |
| イナズマ線の点：オフセット k（整数）は「k 稼働日目の終わり」、0 は開始日の始まり | 予定どおりの点が、進捗管理日の縦線（その日の終わり）にちょうど乗る。土日のマスに点が入らない |
| 「予定どおり」の判定に小さな許容幅を入れた（→ 下の「画面デザインとの突き合わせ」で切り捨て比較に変更） | 3 日タスクの 1 日目は 33.33…% のように割り切れない。同じ値なのに浮動小数の誤差で「遅れ」にならないように |
| 遅れ日数 =（あるべき率 − 実際の率）× 予定日数（→ 同じく小数第1位までに変更） | PDF の遅れタスク一覧に出す |
| プロジェクト全体の進捗率は、予定日数で重み付けした平均 | 1 日タスクと 10 日タスクを同じ重さで平均すると実態とずれる |
| ファイル名テンプレートは、拡張子がなければ付ける | 利用者が拡張子を書き忘れても、Excel・PDF として開けるように。記号の意味は解釈しない |
| DB の排他制約違反の判定（`isParallelTaskViolation`）は、Drizzle が包んだエラー（`cause`）もたどる | Drizzle は pg のエラーを包んで投げることがあるため |
| 衝突の説明文は、見る人がメンバーでないプロジェクトなら「別プロジェクトの予定」とだけ出す | 指示書 §6 の権限ルール |

### 残課題
- `findOverlaps` は純粋関数（既存タスクの配列を受け取る）。DB から同じ担当者のタスクを取ってきて渡す部分は、タスク保存の Server Action（タスク6）で作る
- メンバー分複製（`duplicateForMembers`）で作った各タスクの R3 判定も、タスク6で保存するときに行う

### 矛盾していた点と決めたこと
| # | 矛盾・不足 | 決めたこと | 理由 |
|---|---|---|---|
| 1 | 画面仕様は「完了済みと未着手のタスク、フェーズ行は縦線の上」。ルールの計算では完了済みは終了日、未着手は開始日に点が来る | **完了済み（100%）と未着手（開始日が進捗管理日より後で 0%）は縦線の上に置く**（`isOnStatusLine`・`statusLinePosition`）。フェーズ行はガント側で `statusLinePosition` を使う。開始前でも進めていれば実際の位置（先行）に置く | 授業のイナズマ線の描き方に合わせる。終わったタスク・まだのタスクで線が大きく振れると、本当の遅れ・先行が読みにくい |
| 2 | 進捗率は整数で入力するのに、あるべき率は 33.33…% になる。3 日タスクの 1 日目に 33% と入れると「遅れ」になっていた | **あるべき率の小数を切り捨てた値を下回れば遅れ**、あるべき率を上回れば先行、その間は予定どおり（`onTrackThreshold`）。例：33.33…% → 32% 遅れ、33% 予定どおり、34% 先行 | 整数しか入力できないのに、予定どおりに進めた人が「遅れ」になるのはおかしい |
| 3 | 画面は「予定より 約1.4日 遅れ」。ルールの計算は切り上げの整数だった | **遅れ日数は小数第1位まで**。遅れているのに 0.0 日と出ないよう最小 0.1。予定どおりの範囲（2 の切り捨て）なら 0 | 画面の表示に合わせる。切り上げると 0.2 日の遅れも「1 日遅れ」になり大げさ |
| 4 | 画面にはプロジェクトのアイコンと6色のパレットがある。DB は色を自由な #RRGGBB で持ち、アイコンの列がなかった | `projects.icon`（lucide のアイコン名、既定 `calendar`）を追加。**色は6色だけ**を DB の CHECK と入力チェックで許す。既定は紫 `#7C5CFA`。薄い色（tint）は DB に持たず `src/lib/project-style` から引く | 色の上に文字を載せない・tint と組で使うデザインなので、パレット外の色は表示が崩れる |
| 5 | メンバーカードに肩書き（「デザイン担当」など）がある。ユーザー表に列がなかった | `user.title`（任意）を追加。Better Auth の `additionalFields` で登録時に入れられるようにする | 招待から登録するときに入力する（タスク5） |
| 6 | 困りごとの「手を貸す」ボタンが何をするか書かれていない | **押した人を解決者として困りごとを解決済みにする** | 指示書の「解決者と解決日時を記録する」に合う。作るのはタスク9 |
| 7 | WBS の並べ替えの方法が書かれていない。指示書ではガントのドラッグ編集は作らない | **↑↓ ボタンで並べ替え**。ドラッグは第2版 | 1.5日の開発でドラッグは重い |

### 細かく合わせること（各画面のタスクで反映）
- デザイントークンは `globals.css` の `@theme` に書く（Tailwind v4 は設定ファイルを使わない）

- 日数の表記は「n稼働日」にそろえる

### 「登録したプロジェクトは誰でも入れる？」への答え
- いまの実装では、新規登録は誰でもでき、プロジェクトの画面はまだない。このまま画面を作ると、ログインした人は誰でも全プロジェクトを見られてしまう
- タスク5で次のようにする
  - **新規登録は招待リンク（`/invite/[token]`）からだけ**。ログイン画面の「新規登録」はなくす。招待から名前・肩書き・パスワードを入れて登録する
  - プロジェクトの画面・操作はすべて、サーバー側で `project_members` に入っているかを確かめる。メンバーでなければ 404
  - メンバーボードに出すのは、自分と同じプロジェクトに入っている人だけ。その人の別プロジェクトのタスクは「別プロジェクトの予定」とだけ出す（指示書 §6）

### 残課題
- 本番 DB（`production` ブランチ）には `0001`〜`0003` をまだ適用していない。タスク5を本番に出す前に適用する（→ タスク5で `0004` も追加）

| 決めたこと | 理由 |
|---|---|
| 新規登録は、Better Auth の DB フック（ユーザー作成の直前）で「有効な招待があるメールか」を確かめる | ログイン画面から登録欄を消すだけだと、API を直接呼べば登録できてしまう。フックなら画面・API のどちらから来ても止まる |
| ただし、ユーザーが 0 人のときだけはログイン画面から登録できる | 最初の 1 人がいないと、誰もプロジェクトを作れず招待もできない |
| 招待メールは送らない。owner が招待リンクをコピーして本人に渡す | 指示書でメール通知は「作らないもの」。Discord などで渡せば足りる |
| 招待に役割（`invitations.role`）の列を足した | 画面仕様の「メンバー招待（メール＋役割）」。受諾したときにこの役割でメンバーになる |
| 同じ人への未受諾の招待を作り直すと、古いリンクは消える | 有効なリンクを 1 本にして、どれが生きているか迷わないように |
| 招待のメールアドレスは小文字にそろえて保存・比較 | Better Auth は登録時にメールを小文字にする。大文字まじりで招待すると受諾できなくなる |
| 招待は「受諾済みにする更新」が成功したときだけメンバーに追加（1 つのトランザクション） | 「参加する」を 2 回押しても、1 回だけ処理される |
| メンバーでないプロジェクト、owner でない人の設定画面は 404 | 403 にすると「そのプロジェクトがある」ことが分かってしまう（指示書 §6） |
| オーナーが 1 人もいなくなる役割変更はできない | 設定を変えられる人がいなくなるのを防ぐ |
| プロジェクト作成者が owner になる。作成はログインしていれば誰でもできる | 指示書の画面表で `/projects` は owner。作った人がその owner になる、と読んだ |
| ログイン後の戻り先（`?next=`）は、サイト内のパスだけ許す | `//evil.example.com` のような外部への飛ばしを防ぐ |
| ログイン・招待・404 は同じ白カード（`AuthCard`）で作る | 画面仕様 §5-6「同じ部品・トーンで作る」 |
| フォントは Noto Sans JP・Zen Maru Gothic・JetBrains Mono を `next/font` で読み込み、日本語フォントは preload しない | 日本語フォントは大きく、preload すると最初の表示が遅くなる |

### 起きた問題と対処
- 招待されていないメールで API から登録できてしまった → 開発サーバーが古い認証設定のまま動いていた（認証の API のファイルが作り直されていなかった）。作り直されたあとは 403 になることを確かめた。ほかの部分は、作り直したあとの状態で確認した

### 残課題
- ~~本番 DB（`production` ブランチ）に `0001`〜`0004` を適用してから本番に出す~~ → 2026-11-19 に適用済み（下の「本番 DB へのマイグレーション適用」）
- ~~メンバーを外す操作は作っていない~~ → 下の「招待リンクの取り違えと、メンバーを外す機能」で追加
- チームボードで「同じプロジェクトの人だけ表示・別プロジェクトのタスクは伏せる」はタスク8で作る
- パスワードを忘れたときの再設定はない（メール送信を作らないため）。必要なら owner が招待し直す運用にする

## 本番 DB へのマイグレーション適用

- 実施：2026-11-19（`feature/rules` を main にマージする前）
- 対象：Neon の `production` ブランチ。`0000` だけ適用済みだった状態から、`0001`〜`0004` を適用した
- 理由：`feature/rules` で Better Auth にユーザーの肩書き（`user.title`）を足したため、列がないまま本番に出すとログインで失敗する

### 手順
- 本番の接続文字列（pooling OFF）は `.env.production.local` に置く（git には入らない）
- 接続先のホスト名が dev と違うことを確かめてから、その値を `DATABASE_URL_UNPOOLED` に入れて `pnpm db:migrate`。`drizzle.config.ts` が読む `.env.local` は、すでにある環境変数を上書きしないので、本番に向く

### 確認結果
- マイグレーション履歴 5 件、既存のユーザー 1 人はそのまま
- 8 テーブル、R3 の排他制約（`no_parallel_tasks`）、`btree_gist`、`user.title`・`projects.icon`・`invitations.role` の列がある
- 本番に向けて `pnpm db:check`：28 件成功 / 0 件失敗（ロールバックするのでデータは残らない）

## 招待リンクの取り違えと、メンバーを外す機能

- 実施：2026-11-19（タスク5の追加分）

### 起きたこと
- 本番で、友達 A のメールアドレス宛てに作った招待リンクを、別の友達 B が使って登録・参加してしまった
- B のアカウントが **A のメールアドレスで** 作られ、しかも招待がオーナー役だったため、B が minebook のオーナーになっていた
- 原因：招待リンクは「持っている人なら誰でも、そのアドレスで登録できる」仕組みで、アドレスが本人のものかは確かめていない（確かめるにはメール送信が要るが、指示書でメール通知は作らないもの）

### 対処
- 本人（オーナー）の了解を得て、本番 DB から B のアカウントを削除した（ログイン情報・セッション・メンバー登録もまとめて消える。担当タスク・困りごとが 0 件であることを確かめてから、1 つのトランザクションで実行）
- A には改めて招待リンクを作り、B には B 自身のアドレス宛てに別の招待を作る

### 再発したときに画面で直せるように
- プロジェクト設定のメンバー一覧に **「外す」ボタン** を追加。押すとその場で確認が出て、もう一度押すと外れる
- 外せないとき：自分自身／最後のオーナー／そのプロジェクトで担当しているタスクがある人。理由を画面に出す
- 外すのはプロジェクトのメンバーからだけで、アカウントは消さない（ほかのプロジェクトに入っていることがある）
- 判定は `src/lib/projects/members.ts` の純粋関数（`memberRemovalBlocker`・`roleChangeBlocker`）にまとめ、役割の変更もこれを使うようにした
- 招待の説明文に「リンクを持っている人なら誰でも、そのメールアドレスで登録できてしまう。本人以外に見えるところには貼らない」と書いた

### テスト結果
- Vitest：5 ファイル・132 件成功 / 0 件失敗（5 件追加：外せる／担当タスクあり／自分自身／最後のオーナー／役割変更）
- lint・型チェック・ビルド：成功
- ブラウザ（ローカル、Neon の `dev` ブランチ）：担当タスクがあるメンバー →「担当しているタスクが1件あるため外せません…」。タスクを消すと外せて、メンバーが 1 人に減る。外された人がログインしてそのプロジェクトを開くと 404。自分の行には「外す」ボタンが出ない。確認用のデータは最後に消した

### 残課題
- 取り違えそのものを防ぐなら、招待から登録するときに招待先のメールアドレスを本人に打ってもらう（一致しなければ登録できない）方法がある。未実装
- 外された人のアカウントは残る。アカウントを消したいときは、いまは DB で消すしかない

## 6. WBS 編集

- 成果物：`/projects/[id]/wbs`
  - 目的 > フェーズ > タスクの3階層。オーナーは追加・名前の変更・削除・↑↓ での並べ替えができ、メンバーは同じ表を読み取り専用で見る

  - 保存の Server Action（`src/app/(app)/projects/[id]/wbs/actions.ts`）、読み込みと R3 用の問い合わせ（`src/lib/wbs/server.ts`）、純粋関数（`src/lib/wbs`：並べ替え・休みの補足・ルールチェック欄）

- `pnpm test`（並べ替え・期間内の休み・ルールチェック欄）

### テスト結果
- Vitest：6 ファイル・139 件成功 / 0 件失敗（7 件追加）。`pnpm db:check`：28 件成功。lint・型チェック・ビルド：成功
- ブラウザ（ローカル、Neon の `dev` ブランチ）。確認に使ったユーザー・プロジェクトは最後に消した
  - 目的・フェーズ2つを追加 → タスクを追加
  - 空のまま保存 → タスク名・成果物・開始日・終了日にエラー、保存ボタンは押せない
  - 開始日に 11/23 → 「予定開始日（11/23（月））は勤労感謝の日です」
  - **別プロジェクト（オーナーはメンバーでない）で同じ担当者が持つタスクと期間が重なる → 入力中に衝突を表示。プロジェクト名・タスク名は「別プロジェクトの予定」と伏せて表示**。「12/3（木）から始める」を押すと、同じ稼働日数で 12/3〜12/4 にずれて保存できた
  - 12/28〜1/5 → 「予備期間（バッファ）に入っています」の警告。保存はでき、ルールチェック欄のバッファが NG（2稼働日食い込み）になる。稼働日は 6日（1/1・1/2・1/3 は数えない）
  - メンバー分複製：2人を選び、1人が別プロジェクトで期間が重なる → サーバーが拒否して1件も作らない。重ならない期間にすると2件できる
  - ↑↓ で並びが変わる。編集では自分自身とは衝突しない。Esc でモーダルが閉じる
  - メンバーでログイン → 表は見えるが、追加・編集・並べ替えのボタンは出ない

### 決めたこと・その理由
| 決めたこと | 理由 |
|---|---|
| 入力中の衝突チェックはサーバーに問い合わせる（入力が止まって 0.25 秒後） | R3 はプロジェクトをまたいで判定する。見る人がメンバーでないプロジェクトのタスクは画面に渡せないので、サーバーで判定して、伏せた形だけ返す |
| 保存時もサーバーで同じ判定をし、DB の排他制約違反（23P01）も同じ日本語にする | 画面を通らない呼び出し・同時保存でもすり抜けない（UI・サーバー・DB の3重） |
| 「メンバー分複製」は、1人でも期間が重なれば1件も作らない（全員分を1つのトランザクションで） | 一部だけできると、どれができたか分かりにくい |
| 並べ替えは ↑↓ ボタン（ドラッグは第2版） | 突き合わせで決めたとおり（決めたこと #7） |
| 画面仕様の「表の末尾のインライン追加行」は作らず、「＋ このフェーズにタスク」でモーダルを開く | 時間が足りないため。入力項目・ルールの表示はモーダルで同じように出せる |
| 日付ピッカーで土日祝を選べなくする代わりに、選んだ直後にその場でエラーを出す | ブラウザ標準の日付入力は、特定の日だけ無効にできない。保存はサーバーでも拒否する |
| 休日のエラー文の日付を `11/23（月）` の形にした | 画面の文言ルール（SCREENS.md §7） |
| 目的・フェーズを消すときは、その場で確認を出す（配下も消えると書く） | 配下のタスクがまとめて消えるため |

### 残課題
- 進捗率・実績日・成果物 URL の更新はこの画面では作っていない（担当者が自分のカードから更新する。タスク8）
- 目的が複数あるときの「＋ フェーズ」（ヘッダー）は最後の目的に足す。各目的の下のボタンからも足せる
